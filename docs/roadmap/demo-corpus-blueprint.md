## Rationale

EXTEND the existing VP-400 universe rather than start fresh, then formalize it into a company and a two-device family. Three reasons. (1) The four existing fixtures (capa-001, fmea-vp400, rmf-vp400, sop-qsp-0012) already carry a coherent, load-bearing web of planted contradictions — severity 3-vs-4, threshold 20-vs-15, 35k-vs-41k units, software 3.2.1-vs-4.2, review-after-release, HAZ-03 residual 20 declared "acceptable." Discarding them wastes hand-authored anchor text the eval labels already point at; extending them turns four isolated files into one dense graph and preserves every existing label. (2) An infusion pump is the textbook cumulative-change / letter-to-file case (the RAPS worked example is literally software + labeling + temperature + electrical + geometry changes to a pump), so it is the right vehicle for feature 3 with zero re-domaining. (3) A device FAMILY (VP-400 + SP-200 sharing a board) buys the cross-device propagation story the single-device fixtures cannot tell, and a cleared K-number baseline buys the GP7 "compare to the original device, not the last internal revision" story. DESIGN INTENT: the corpus is engineered so that (a) every one of the 12 FACT_KINDS in facts.ts appears in at least two documents so the deterministic findDiscrepancies() diff lights up; (b) the reference graph is dominated by deterministic edges (contains/references/governed_by/escalates_to/closes/modifies/verifies-from-matrix) with model-only edges confined to the risk chain, so the spider map has a completeness floor and absence-findings are assertable; (c) the corpus-completeness gate is satisfied for every orphan/unverified finding (the counterpart document class is always present); (d) planted defects are spread across compliance, conformance, consistency, completeness, and plausibility so the demo exercises all five check passes plus the deterministic consistency pass. LICENSING GUARDRAIL (applies to every document generated from this spec): all prose hand-authored and original. Nothing is copied or paraphrased line-by-line from OpenRegulatory (CC BY-NC-SA), from ISO 13485 / ISO 14971 / IEC 62304 (copyrighted — clause IDs and clause titles ONLY, our own expectation prose), or from any vendor template (Greenlight Guru, Jama, Ketryx, Qualio, etc.). FDA correspondence (the Form 483) is original fictional text keyed to CFR paragraph numbers — it must NOT reproduce any real warning letter or 483, and must not name any real firm. The 510(k) Summary is our own fictional device description. No public-corpus prose (FDA deficiency sentences, guidance excerpts) is embedded in any customer document, so it never contaminates the verbatim-quote hallucination guard. Doc-ID cross-references use prefixes the extractor regex in extract/text.ts already recognizes (CAPA/NCR/CR/COMP/DCO) plus new ones (K-number, DI/DO/VER/VAL/TM/RMP/RMF/FMEA/HAZ/FM/RC/IFU/QSP/CA) that require the regex-prefix widening the traceability research already calls for — flagged per-edge below.

Caught by the DETERMINISTIC consistency pass — findDiscrepancies() clusters risk_severity facts on the shared subject 'spurious occlusion alarm causing infusion interruption' (subjectsMatch containment handles the FMEA 'FM-201' prefix) and emits a consistencyFinding under rule regreview-logic-risk-rating-consistency.

### PD-02 — consistency / high
Spans: CAPA-2026-0142, RMP-VP400, RMF-VP400, FMEA-VP400

Risk-index ACCEPTABILITY THRESHOLD disagreement: CAPA-2026-0142 §4 uses 20; RMP-VP400, RMF-VP400 §2 and FMEA-VP400 §3 all use 15. Using the looser 20 lets the CAPA reach an 'acceptable' conclusion the plan would not support. Caught by the deterministic consistency pass on risk_acceptability_threshold (a DOCUMENT_SCOPED kind, so subject wording is ignored and the kind alone joins them).

### PD-03 — consistency / low

### PD-04 — consistency / medium
Spans: CAPA-2026-0142, RMF-VP400, FMEA-VP400, VER-2026-014

SOFTWARE IDENTITY conflation: the same occlusion-alarm behavior is attributed to application software v3.2.1 (CAPA-2026-0142, FMEA-VP400) and to safety-controller firmware v4.2 (RMF-VP400, VER-2026-014); no document disambiguates application software from safety firmware. Caught by the deterministic consistency pass on software_version (document-scoped) as a 3.2.1-vs-4.2 disagreement, and by the plausibility pass as an ambiguity that makes the CAPA's 'software ruled out' claim unfalsifiable.

### PD-05 — plausibility / medium

## Distractors (text that looks like a defect but is correct)

- D-01 (RMF-VP400 HAZ-04, air-in-line): residual severity 4 EQUALS initial severity 4 after the control. This pattern-matches to an iso14971-7.3 'residual risk not reduced' defect, but it is CORRECT: no severity reduction was claimed (only probability was already Remote), and the severity of a harm does not drop merely because a control was added. The demo should NOT flag it — contrast HAZ-01, where a severity drop IS claimed and IS justified.
- D-02 (CAPA-2026-0142 vs CAPA-2026-0114): two occlusion-alarm CAPAs with near-identical titles look like a duplicate or mis-numbered record. They are DISTINCT failure modes — spurious alarm (0142) vs failure-to-annunciate (0114) — with correct, different requirement_id values. Do NOT flag as an ID inconsistency.
- D-03 (FMEA-VP400 detection rating D vs RMF-VP400): the FMEA carries an S/O/D + RPN with a detection score; the RMF uses severity x probability with no detection term. A naive reconciler will try to align 'detection' across the two files. This is WRONG by construction — detection is an FMEA/RPN construct with no ISO 14971 counterpart; risk_detection facts must never be diffed against RMF values. No finding.
- D-04 (CAPA-2026-0142 arithmetic): 'Severity 3 x Occurrence 2 x Detection 2 = risk index 12' is internally consistent given the stated inputs. The 12 is NOT itself a defect — only the severity input (3, should be 4 per FMEA) and the threshold (20, should be 15) are. Do not flag the multiplication or the 'below threshold' arithmetic in isolation.
- D-05 (VER-2026-014 sample size n=5): the verification uses n=5 and states a pre-defined attribute acceptance criterion with a reliability/AQL basis in its protocol — this n=5 is JUSTIFIED for its purpose. It looks identical to the CAPA's unjustified n=5 (PD-07) but is correct. The demo should fire the sample-size rule on the CAPA and show RESTRAINT here.
- D-06 (IFU-VP400 scope 'software version 3.2.1 and later'): reads as an open-ended, unbounded scope statement, but it is a CORRECT, bounded configuration statement (every shipped unit is at or above 3.2.1). Not a vague-scope or evidence-locatable defect.
- D-07 (COMP-2026-0207 second complaint line): a second, minor complaint on the same record is correctly determined non-reportable with a recorded rationale (device performed to specification, no patient harm, no malfunction meeting the reporting threshold). The complaint->reportability rule (PD-09) must NOT fire here — this shows the linkage check discriminating, not blanket-flagging every complaint.
- D-08 (K192214 software v3.1.4 vs field v3.2.1): the cleared predicate documents v3.1.4 while current field units run v3.2.1. This is NOT a consistency defect — it is the expected, documented version progression from a 2019 clearance to the 2026 field state, not two documents disagreeing about the same unit. Distinguish from PD-04, which is a same-behavior application-vs-firmware conflation.

## Cumulative-risk demo narrative

FEATURE-3 DEMO SCRIPT — "individually benign, collectively significant." Since the VP-400's 2019 clearance (K192214, application software v3.1.4), Northlake made six changes to the occlusion-sensing signal chain, each documented as a letter-to-file / non-significant change, none triggering a new 510(k) on its own. The cumulative ledger inside CA-2026-011 lists them:

(1) 2021 — Software v3.1.4 -> v3.2.1: occlusion pressure-threshold parameters 'tuned.' LTF'd as a return-to-spec adjustment (change guidance software Q2). Individually: plausible non-significant.
(2) 2022 — Battery: Li-ion cell supplier change, 'equivalent capacity.' LTF'd as a like-for-like electrical component swap. Individually: benign.
(3) 2023 — Administration-set cassette elastomer: silicone durometer change (DCO-2023-0044, supplier-driven). LTF'd as a materials change with no fluid-path performance impact claimed. Individually: benign.
(4) 2024 — Cassette-channel geometry: chamfer added to reduce angled seating (DCO-2026-0031, the CAPA-2026-0142 corrective action). LTF'd, and applied to NEW PRODUCTION ONLY with no disposition of distributed units (PD-06). Individually: minor.
(5) 2025 — Pressure transducer part substitution on the shared PCA-4400 board (DCO-2025-0077), obsolescence-driven, 'characterized equivalent.' LTF'd; propagated to neither the aggregate assessment nor SP-200's risk file (PD-16). Individually: minor.
(6) 2026 — Safety-controller firmware v4.1 -> v4.2: adds a secondary pressure check and the occlusion alarm credited in RMF-VP400 as the HAZ-01 control (CA-2026-011). Per change guidance software Q3a/Q3b this ADDS/MODIFIES a risk control and touches a hazard cause in the risk management file — the one change most likely to trip the threshold, and it is being LTF'd anyway.

WHY THE SUM IS SIGNIFICANT: changes 1, 3, 4, 5 and 6 all act on the SAME function — occlusion detection — that was the basis of the cleared device's substantial-equivalence claim. The pressure-sensing behavior of the 2026 device (new transducer + new channel geometry + new elastomer + retuned threshold + new firmware alarm logic) is materially different from the 2019 cleared device, even though every step was individually small. This is exactly GP4 (a modified risk: the risk score and the DURATION of the occlusion-detection risk have moved — FMEA now carries FM-201 at index 24) and GP6/GP7 (assess changes 'separately AND in aggregate,' against the ORIGINAL cleared device).

WHAT THE TOOL OUTPUTS (deterministic, NOT a verdict): the cumulative ledger view renders the six changes as a spider map converging on the occlusion-detection node, and flags, each with a verbatim quote: (a) CA-2026-011's comparison table uses the last internal revision (v4.1) as its comparator instead of the cleared baseline K192214 — a GP7 violation and a deterministic mismatch against QSP-0015 (PD-15); (b) no aggregate assessment of the five subsystem-touching changes exists (GP6); (c) five of six changes touch the occlusion-detection subsystem, with the risk index for FM-201 having moved from its cleared-baseline value to 24 (drift metric); (d) change (6) adds a new risk control (software Q3b) yet is filed as non-significant; (e) change (4) never dispositioned distributed units and change (5) never propagated to SP-200. The framing is 'here is your cumulative drift and here is where the justification is thin,' mirroring the PCCP Impact Assessment structure (element 4: how each modification impacts another; element 5: cumulative impact of all modifications) — the tool refuses to issue the submit/don't-submit determination, which is statutorily the manufacturer's.
